# 상담 구조 1과 3의 첫 비교

2026-11-20에 팀원의 도구 호출형 상담(1번, PR #121 `8dcf025`)과 채팅 에이전트·팀장·추천·검증 워커를 둔 상담(3번)을 실행했다. 두 구조 모두 사용자가 요청한 기술을 골랐다. 3번은 실제 추천 두 건에서 모두 워커 실패를 보고하고 과정 카드를 보류했다. 이 표본으로 팀장의 효과나 채택할 구조를 확정하기 어렵다.

## 같은 조건으로 실행한 부분

- 같은 클라우드 직무, 빈 프로필, 같은 모델 설정과 입력 가드레일을 사용했다. 각 구조는 독립된 대화와 빈 추천 캐시로 시작했다. 한 대화 안에서는 이전 발화와 답을 이어받았다.
- 채용 수요는 `data/sample/demand.json`, 과정 후보는 저장소 카탈로그의 규칙 검색으로 고정했다. 실측은 Bedrock의 발화 해석, 도구 선택, 추천 작성·검토, 팀장 결정에 해당한다. 배포 환경의 KB 검색과 DynamoDB 조회 시간은 측정 범위 밖이다.
- **대상 선택**은 추천 API에 전달한 기술로 확인했다. **근거 전달**은 1번의 최종 문장 또는 3번 카드에서 검토를 거친 과정과 추천 이유 원문을 확인하는 엄격한 검사다. 원문 불일치만으로 바꿔 쓴 내용의 의미가 틀렸다고 판단할 수는 없다.

## 실제 Bedrock 실행

Kubernetes의 첫 짝비교에서는 합산 모델 호출 14회 중 1번이 11회를 사용했다. 3번은 3회·5,798토큰·9.3초에서 상한에 도달했다. 위 표의 마지막 행은 3번만 새 대화에서 다시 실행한 값이다. 중단분을 포함한 **실제 총량은 모델 42회, 110,229토큰, 입력 가드레일 7회**다.

두 사례 모두 개발 문항이며 각 구조의 완주값은 사례당 한 번이다. Terraform 측정 후 3번의 워커 실패 답변에도 결과 검토를 적용했고 평가기의 캐시 초기화 및 실패 기록을 보강했다. 따라서 시간은 각 실행의 관찰값이다. 첫 측정의 실패 세부 사유는 수집하지 않았다. 후속 실행에서는 추천 작성·검토·수정 단계와 예외 종류를 기록하며 원문은 보관하지 않는다.

## 모의 회귀 검사

개발 대화 7개·15턴에서 3번은 명시한 추천 대상 4/4, 학습 희망 지칭 1/1, 첫 번째 Gap 기술 지칭 1/1, 보유 기술 정정 1/1, 불명확한 지칭 되묻기 1/1, 미요청 추천 방지 9/9, 검증 근거 전달 6/6을 충족했다. 1번은 15턴 중 14턴에 기본 모의 대본을 재생했다. 두 구조의 모의 결과는 인터페이스 회귀 검사에 사용한다.

## 재현과 결과 파일

실행 명령은 [상담 화면 실행 문서](../../app/README.md#팀장-에이전트-상담-실행)에 있다. `--method 3`을 추가하면 동일한 사례의 3번만 새 세션에서 실행한다. 개발 문항은 [대화 세트](../../data/eval/supervised_conversations_dev.json)에 있다.

이번 실행의 로컬 결과는 `outputs/eval/` 아래에 있다.

- `supervised_compare_bedrock_1795114840555577908.json` — Terraform 두 턴
- `supervised_compare_bedrock_1795114987735062267.json` — Kubernetes 짝비교 및 상한 도달
- `supervised_compare_bedrock_1795115096154423606.json` — Kubernetes 3번 단독 재실행
- `supervised_compare_mock_1795115179472292935.json` — 개발 대화 7개 전체
