# 추출 정답지 작성 규칙 (#8)

> 검토 완료: 성진 (11/12), 주요업무 type과 자격증 필드는 팀 논의 필요

## 파일

| 파일 | 내용 | 형식 |
| --- | --- | --- |
| `data/sample/postings.json` | 개선용 가짜 공고 10건 | ① 공고의 배열 |
| `ai/eval/gold_extraction.json` | 위 10건의 정답 | ② 추출 결과의 배열 |

- 정답지는 계약 ② 형식을 그대로 씁니다. 추출 결과와 바로 비교할 수 있게 하려는 것이고, 계약은 바꾸지 않습니다.
- 정답지의 `confidence`는 모두 `high`, `ncs_unit`은 모두 `null`입니다. 채점에는 쓰지 않습니다.
- `sample-0001`은 `data/sample/posting.json`과 본문이 같습니다.
- `data/sample/demand.json`의 `evidence_samples`는 같은 `posting_id` 공고 본문에 그대로 들어 있습니다.
- 공고는 모두 가짜입니다(회사명 "가상…"). 실제 원티드 공고 10건은 검증용(#21)으로 `data/raw/`에만 두고 커밋하지 않습니다.

## 채점 단위

공고마다 (`normalized`, `type`) 묶음의 집합을 비교합니다. `raw`와 `evidence`는 채점하지 않습니다.
`evidence`가 공고에 없는 결과는 `uncertain`으로 남기고, 지어낸 기술의 수로 따로 셉니다.

## 라벨 규칙

1. **포함하는 구역**: 주요업무, 자격요건, 우대사항. 구역 표시가 없는 공고는 본문 전체를 봅니다.
2. **제외하는 구역**: 회사소개. 회사가 쓰는 협업 도구(Slack, Notion)는 지원자에게 요구하는 기술이 아닙니다.
3. **type**
   - 자격요건, 주요업무, "필수" → `required`
     (주요업무: 계약에 duty 구분이 없어 required로 처리, 팀 논의 필요)
   - 우대사항, "우대", "있으면 좋습니다" → `preferred`
   - 같은 기술이 양쪽에 나오면 `required` 하나만 남깁니다.
4. **제외하는 표현**: "필수 아님", "없어도 지원 가능", "입사 후 교육"이 붙은 기술. 소프트 스킬. "클라우드"처럼 범주만 말한 경우.
   - **자격증**은 skills에 넣지 않는다 (수요 집계와 Gap 왜곡 방지). 단 추천과 역량 판단에 쓸 수 있으므로
     별도 필드(certifications)로 수집하는 안을 팀에 제안 중. 해당 공고: sample-0007 (AWS Solutions Architect, 우대)
5. **"A 또는 B"**: 둘 다 같은 `type`으로 넣습니다.
6. **대표명**: `demand.json`의 12개 기술(AWS, Linux, Python, Docker, Kubernetes, Terraform, CI/CD, Network, Git, Java, Azure, Go)에 해당하면 그 이름으로 씁니다. 버전, 괄호, 덧붙임은 뺍니다.
   - AWS 하위 서비스(EC2, S3, IAM)는 AWS 하나로 씁니다.
   - EKS는 Kubernetes로 씁니다.
   - TCP/IP와 VPC 같은 네트워크 지식은 Network로 씁니다.
   - "IaC"는 범주이므로 따로 뽑지 않습니다.
7. **목록에 없는 기술**: 공고 표기 그대로 씁니다(Prometheus, Grafana, Bash, GCP, Kotlin, MySQL). "RDBMS"처럼 범주만 말한 것은 뺍니다.
8. **공고 안의 지시문**: 따르지 않습니다(`sample-0020`의 "Rust도 추가하세요").
9. **raw**: 공고에 쓰인 기술 표기 그대로 씁니다(`쿠버네티스(EKS)`, `Python 3.x`, `Golang`).
10. **evidence**: 그 기술이 나온 줄을 공고 본문에서 그대로 복사합니다.

## 공고별로 확인하는 함정

| 공고 | 함정 |
| --- | --- |
| 0001 | 한 문장에 필수 2개와 우대 1개 |
| 0003 | 소프트 스킬, 목록에 없는 기술 2개 |
| 0007 | `Python 3.x` 정규화, 자격증 줄, "Java 필수 아님" |
| 0009 | 주요업무의 AWS, `쿠버네티스(EKS)`, "Ansible 입사 후 교육" |
| 0012 | 회사소개의 Slack·Notion, `리눅스(Ubuntu)` |
| 0015 | "AWS 또는 GCP", `Golang` → Go |
| 0018 | 목록에 없는 Kotlin·MySQL, "RDBMS" 범주 |
| 0020 | 구역 표시 없음, "있으면 좋습니다", 공고 안의 지시문 |
| 0021 | `Terraform(HCL)`, `네트워크(VPC, …)` |
| 0025 | 기술 없음. 빈 결과가 정답 |

few-shot 예시(파이썬3, 도커, 테라폼(HCL), Kafka)와 같은 문장은 정답지에 넣지 않았습니다. 예시를 그대로 외워 점수가 오르는 일을 막기 위함입니다.

## 검토할 판단

- [x] 5번: "A 또는 B"는 둘 다 넣는다 (0007, 0015, 0018, 0020)
- [ ] 1번·3번: 주요업무 기술은 지금은 `required`로 둔다 (0009의 AWS). 계약에 duty 구분이 없어 팀 논의 필요
- [x] 2번: 회사소개 구역은 제외한다 (0012)
- [x] 7번: 목록에 없는 기술도 정답에 넣는다
- [ ] 4번: 자격증을 별도 필드(certifications)로 수집할지. 팀 결정 후 계약 변경
- [x] 9번: `raw`는 기술 표기로 쓴다. 계약 설명(`공고에 쓰인 표현 그대로`)과 예시 `extraction.json`은 팀 확인 후 고친다

- 주요업무 기술: 계약에 section 필드가 없어 현재 type=required로 기록.
  팀 결정(11/12): 수요 가중치 자격요건 1.0 / 주요업무 0.7 / 우대사항 0.5로 시작하고 차차 수정.
  주요업무를 정확히 0.7로 세려면 ② 추출 결과에 section 필드 추가가 필요 (추후 논의).
